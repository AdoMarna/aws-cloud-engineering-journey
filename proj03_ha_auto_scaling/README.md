# proj03_ha_auto_scaling — High Availability, Load Balancing & Auto-Scaling

Fully automated, idempotent provisioning of a two-tier, multi-AZ web stack:
an internet-facing Application Load Balancer distributing traffic across
two private subnets, backed by an Auto Scaling Group that keeps 2 to 4
Nginx instances healthy, self-heals on failure, and scales out on CPU
load. Instances are never exposed directly to the internet — the ALB is
the only public entry point. No console clicks — everything is built and
torn down through `aws-cli v2` and `bash`.

## Architecture

```
                              Internet traffic
                                     │
                                     ▼ (port 80)
                    ┌────────────────────────────────┐
                    │   Application Load Balancer     │
                    │  Public-Subnet-AZ1 / AZ2        │
                    │  SG-ALB: 80 from 0.0.0.0/0       │
                    └────────────┬─────────────────────┘
                                 │ Listener :80 → Target Group
                    ┌────────────┴─────────────────────┐
                    │       Target Group (my-tg)        │
                    │  health check: GET / :80          │
                    │  2 healthy checks, 15s interval   │
                    └────────────┬─────────────────────┘
                                 │
              ┌──────────────────┴──────────────────┐
              ▼                                      ▼
   Private-Subnet-AZ1                      Private-Subnet-AZ2
┌───────────────────────┐            ┌───────────────────────┐
│   EC2 (ASG-managed)    │            │   EC2 (ASG-managed)    │
│   nginx, IMDSv2 only   │            │   nginx, IMDSv2 only   │
│   SG-App: 80 from      │            │   SG-App: 80 from      │
│   SG-ALB only          │            │   SG-ALB only          │
└───────────────────────┘            └───────────────────────┘
              │                                      │
              └──────────────────┬──────────────────┘
                                 ▼
                    Auto Scaling Group (my_asg)
                    min 2 / desired 2 / max 4
                    HealthCheckType: ELB
                    Target tracking: CPU @ 50%
```

Both the ALB (public subnets) and the ASG (private subnets) live in the
VPC created by `proj01_custom_vpc` — this project provisions no network of
its own, it consumes proj01's VPC/subnets by tag lookup. The Launch
Template's IAM instance profile (`EC2-SSM-Instance-Profile`) is the one
created by `proj02_secure_compute` — this is the **only** dependency on
proj02; the AMI is resolved independently via the public SSM parameter
(see Design conventions), so no proj02 instance needs to be running.

## Prerequisites

- `aws-cli v2`, `jq`, `bash`.
- `proj01_custom_vpc` already deployed: this project looks up its VPC
  (`Project=proj01` tag) and all four subnets (`Public-Subnet-AZ1/AZ2`,
  `Private-Subnet-AZ1/AZ2`) by name.
- `proj02_secure_compute` already deployed, specifically the
  `EC2-SSM-Instance-Profile` instance profile — attached to every instance
  the ASG launches, for Zero-SSH access via SSM Session Manager.
- IAM permissions to create security groups, launch templates, target
  groups, load balancers/listeners, Auto Scaling Groups and scaling
  policies.

## Usage

```bash
make            # deploy the full HA stack (~5-10 minutes, incl. ALB + ASG health checks)
make deploy     # same as above
make enable     # attach the CPU 50% target tracking scaling policy
make stress     # SSM stress-ng test on one instance, watches the ASG scale out
make update     # zero-downtime rolling update via Launch Template versioning + Instance Refresh
make simulate   # terminates one instance to test ALB/ASG self-healing
make clean      # tear down every proj03 resource (ASG, ALB, target group, launch template, security groups)
make help       # list all targets
```

Every script is idempotent: running `make deploy` twice in a row never
creates duplicate resources. Each resource is looked up by its `Name` (or
ARN/ID) plus `Project=proj03` tag before anything is created, so a script
can be safely re-run after a partial failure.

## Design conventions

- Every script starts with `set -euo pipefail`.
- Every AWS-created resource carries a standardized `Name` tag plus
  `Project=proj03`, `Environment=dev`, used both for idempotency lookups
  and for cleanup. ASG tags are created with `PropagateAtLaunch=true`, so
  every instance the ASG launches inherits them automatically — this is
  how `stress_test.sh` and `simulate_failure.sh` locate a live ASG
  instance without ever hardcoding an instance ID.
- No hardcoded AMI: the AMI ID is resolved dynamically at every
  `deploy_ha_stack.sh` / `update_fleet.sh` run via the official AWS SSM
  public parameter
  (`/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64`),
  never written in the script or in `templates/launch_template.json`.
- No hardcoded resource ID: `templates/launch_template.json` ships as a
  neutral template with empty placeholders (`ImageId`, `SecurityGroupIds`,
  `IamInstanceProfile.Name`, `UserData`); `deploy_ha_stack.sh` fills it in
  with `jq --arg` at every run (never string concatenation, to avoid
  quoting/injection issues) before calling `create-launch-template`.
- `aws autoscaling` has no `wait` subcommand (unlike `ec2` or `elbv2`), so
  every script that needs to block on ASG state (`deploy_ha_stack.sh`,
  `update_fleet.sh`, `simulate_failure.sh`, `cleanup_ha_stack.sh`) rolls
  its own bounded polling loop instead of an unbounded `sleep`.
- Each resource follows the same inline pattern: `describe`/`get` to check
  if it already exists, `if` to skip creation when it does, `create`
  otherwise.

## Scripts

### `scripts/deploy_ha_stack.sh`

Provisions, in order:

1. `SG-ALB`: allows inbound TCP/80 from `0.0.0.0/0`.
2. `SG-App`: allows inbound TCP/80 **only** from `SG-ALB` — no other
   ingress rule exists, so instances are unreachable except through the
   ALB.
3. Fills `templates/launch_template.json` (AMI via SSM parameter,
   `SecurityGroupIds`, `IamInstanceProfile.Name`, base64-encoded
   `templates/userdata.sh`) and creates the Launch Template (`t3.micro`,
   IMDSv2 enforced via `HttpTokens=required`).
4. `my-tg`: HTTP Target Group on port 80, health check on `/`, 2 healthy
   checks required, 15s interval.
5. `my-load-balancer`: internet-facing ALB across both public subnets,
   waits (`elbv2 wait load-balancer-available`) until active.
6. A Listener forwarding port 80 to the Target Group.
7. `my_asg`: Auto Scaling Group across both private subnets, min 2 /
   desired 2 / max 4, `HealthCheckType=ELB`, 600s grace period; waits
   (`elbv2 wait target-in-service`) until both instances are healthy
   behind the Target Group.

### `templates/userdata.sh`

Runs once at first boot: installs and starts Nginx and `stress-ng`
(needed by `stress_test.sh` — pulled from the default AL2023 repos, no
EPEL required), fetches instance metadata through **IMDSv2 only**
(token-based), and renders a status page showing the instance ID and
Availability Zone — used to visually prove the ALB is load-balancing
across both AZs.

### `scripts/enable_autoscaling_policy.sh`

Attaches a Target Tracking scaling policy (`asg-policy-cpu50`) to `my_asg`
targeting 50% average CPU utilization (`ASGAverageCPUUtilization`). Run
after `deploy_ha_stack.sh`, via `make enable`.

### `scripts/stress_test.sh`

Finds a live ASG instance (by `tag:Project=proj03`), sends
`stress-ng -c 8 --timeout 180s` via `aws ssm send-command`, waits for the
command to finish, then polls the ASG (up to 10 min) until it detects a
3rd instance — proving the CPU-based scaling policy triggers a scale-out.

### `scripts/update_fleet.sh`

Demonstrates a zero-downtime rolling update:

1. Base64-encodes `templates/update_homepage.sh` (a revised homepage) and
   builds the new `UserData` payload with `jq -n --arg` (never raw string
   concatenation, to avoid JSON-escaping bugs).
2. Creates a new Launch Template version (`create-launch-template-version
   --source-version 1`) if version 2 doesn't already exist.
3. Starts an Instance Refresh (`start-instance-refresh`) with
   `MinHealthyPercentage: 100` and `InstanceWarmup: 120` — the ASG never
   drops below full desired capacity, and a freshly launched instance is
   only counted "warm" 120s after reaching `InService`, giving Nginx time
   to actually start before the old instance is retired.
4. Polls `describe-instance-refreshes` until the refresh reports
   `Successful`.

### `scripts/simulate_failure.sh`

Chaos-testing / self-healing proof:

1. Picks a live ASG instance and terminates it directly via
   `aws ec2 terminate-instances` (bypassing the ASG).
2. Waits (`aws ec2 wait instance-terminated`) for it to be fully gone.
3. Polls the Target Group until the terminated instance is deregistered.
4. Polls `describe-scaling-activities` (filtered to activities newer than
   the kill timestamp) until a new `Launching` activity appears.
5. Polls the ASG until it reports exactly 2 `InService` instances that no
   longer include the killed instance ID — the concrete proof of
   self-healing, not just an instance count.

### `scripts/cleanup_ha_stack.sh`

Tears down every resource created above, in dependency order: ASG scaled
to 0 and deleted first (`--force-delete`, then a manual polling loop with
a forced `terminate-instances` fallback, since `aws autoscaling` has no
`wait` subcommand and instance termination can lag behind the ASG's own
state) → Listener → Load Balancer (`elbv2 wait load-balancers-deleted`) →
Target Group → Launch Template (all versions removed with it) → `SG-App`
→ `SG-ALB`. Every step is idempotent — resources already gone are skipped
with a log line instead of failing.

## Security

- **No direct internet exposure**: EC2 instances live exclusively in
  private subnets with no public IP; the ALB in the public subnets is the
  only internet-facing resource.
- **Security Group chaining**: `SG-App` only accepts traffic whose source
  is `SG-ALB` — not a CIDR range — so instances can never be reached
  except through the load balancer, even if someone learns their private
  IPs.
- **IMDSv2 only**: `HttpTokens=required` in the Launch Template blocks
  unauthenticated IMDSv1 requests on every instance the ASG launches.
- **Zero-SSH**: instances are bootstrapped with the same
  `EC2-SSM-Instance-Profile` as proj02 — remote access, if ever needed,
  goes through SSM Session Manager, never SSH.
- No access key, secret, or Account ID is ever written in plaintext in the
  repository. `templates/launch_template.json` is committed as a neutral
  template with empty placeholders; real AMI/SG/IAM values only ever
  exist in the local, gitignored working copy produced by
  `deploy_ha_stack.sh` at runtime.
